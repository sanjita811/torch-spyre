THE GOAL

Why state-space models matter

Mamba-2 is a leading alternative to the Transformer. It processes long sequences in linear time instead of quadratic — a structural advantage for long-context AI.

  • Transformer cost grows with the square of sequence length
  • SSMs stay linear — cheaper as context grows
  • Increasingly used in frontier long-context & efficiency work

The business case

For Spyre to be a credible platform for modern AI, it must run the architectures customers actually want to deploy — not only Transformers.

This project proves SSMs run on Spyre, and turns the accelerator's constraints into a concrete backend roadmap.

THE CHALLENGE

Spyre is not a GPU

Spyre is a tiled, memory-oriented accelerator. Getting an SSM to run well means respecting hardware rules a GPU never imposes.

  • Data laid out in 128-byte blocks — every reshape has a cost
  • No native cumulative-sum, no native attention op
  • Per-core memory limits bound how big any tensor can be
  • Half-precision throughout — overflow is a real constraint

The reference is GPU-shaped

The canonical Mamba-2 kernel is written for GPUs: giant fused operations, large chunk size, cumulative-sums everywhere.

None of it maps directly. The work was re-deriving the same math as Spyre-legal operations — and finding where the hardware pushes back.

THE APPROACH

Decompose the algorithm into Spyre-legal matmuls

The SSD algorithm splits a long sequence into chunks. Each stage — written as one big operation in the reference — becomes a chain of batched matrix multiplies with the decay folded into the operands.

Key techniques: cumulative-sum as a matrix multiply · decay folded into operands (no giant intermediate) · numerically-centered exponentials for half-precision safety · the whole thing fused into one compiled kernel.

Design principle: the kernel is model-agnostic — it computes Y = SSM(X,A,B,C) only. Projections, gating, and normalization belong to the model layer, so the kernel is reusable across any SSM.

TESTING & VALIDATION

A CPU twin separates "our math" from "the backend"

  • Reference oracle: the verbatim Mamba-2 kernel on CPU as ground truth
  • CPU mirror: the exact same op-sequence as our kernel, in plain PyTorch — pinpoints whether a bug is in our formulation or the hardware
  • Device-faithful oracle: a half-precision model that predicts Spyre behavior without a compile — so we tune correctness cheaply

Acceptance metric: relative-L2 error < 0.05 — the realistic half-precision budget.

PROFILING

The kernel is memory-bound, not compute-bound

Deep profiling gave the single most important insight of the project: the math is nearly free — moving data is the entire cost.

Ideal compute: ~17 µs
Runtime: milliseconds

Ideal matrix-multiply work is ~17 µs (the compiler's own cycle model). The kernel runs orders of magnitude longer — the gap is entirely data movement, laying tensors out in the right orientation between operations.

Why this matters strategically

It redirected the entire optimization effort. Chasing compute utilization would have been wasted work.

Every real win came from cutting data movement — fewer layout conversions, smaller intermediates, sharing tensors across operations.

It also tells the backend team exactly where the leverage is: keeping data resident on-chip.

OPTIMIZATIONS

Every win cut data movement

  • Factored decay: fold decay into operands instead of a giant per-chunk matrix — killed a 34 MB intermediate, ~2× faster
  • Shared layouts: reuse one prepared tensor across two matmuls — measured to the minimum number of layout conversions
  • Asymmetric mask build: broadcast one operand in-kernel instead of shipping it — halved a 268 MB transfer to 134 MB
  • Tiling sweep: measured the optimal core-tiling on-card — ~34% faster than the previous default

Rigor over intuition

A recurring lesson: on this hardware, counting operations does not predict speed — a "cheaper-looking" layout can be slower.

So every optimization was measured on-device, and several plausible ideas were rejected when the hardware disagreed. Negative results were recorded so they aren't re-tried.

Default-config error held at 0.0038 through every optimization.

OPTIMIZATION · MEASURED

Finding: GPU's chunk size is wrong for Spyre

GPUs use a large chunk size (256). On memory-bound Spyre, the smallest chunk is fastest — the opposite conclusion.

Default sequence length (4,096). Lower is faster. Measured on-card.

Why smaller wins

The within-chunk work grows with the square of chunk size. Because the kernel is memory-bound, that intermediate dominates — the smallest legal chunk moves the least data.

Takeaway: hardware-specific tuning beats porting GPU defaults. We ship a measured best-config per sequence length.

LONG-CONTEXT ENVELOPE

Correct & running up to 32K tokens

Validated on-device Backend-limited

The maximum sequence length doubled this cycle — from 16K to 32K — by re-measuring a hardware limit against the latest backend.

  • Each length uses its own measured-best chunk size
  • Error stays within budget across the whole range
  • 64K+ is blocked by a specific, identified backend limitation — not by our math
FUTURE WORK

One backend fix unlocks the next frontier

Beyond 32K, one tensor grows past the per-core memory limit. The algorithmic fix is known and CPU-validated — it needs one backend capability.

  • Sub-quadratic scan — validated correct on CPU; the math is ready
  • The blocker: reshaping a tensor into blocks corrupts its layout on-device
  • The ask: correct layout handling across a splitting reshape — one well-scoped capability

Turning a kernel into a roadmap

This project produced a prioritized list of backend capabilities, each with a minimal reproducer and a clear payoff:

Splitting-reshape layout → unlocks 64K+ On-chip residency → cuts the memory tax Layout-sharing across ops → general speedup

Each fix helps not just SSMs, but any memory-bound model on Spyre.
